# Multi-Database MySQL

## Overview
The app uses separate MySQL databases for different concerns, each isolating a Rails 8 "Solid"
subsystem from the primary application data.

## Components
| Database | Purpose |
|---|---|
| primary | Main application data |
| queue | Solid Queue job storage |
| cache | Solid Cache storage |
| cable | Solid Cable WebSocket connections |
| replica | Read-only replica (when configured) |

## Data flow
- Each subsystem reads/writes its own database; application code uses the primary.
- Auto-generated schema files — `db/schema.rb`, `db/cable_schema.rb`, `db/cache_schema.rb`,
  `db/queue_schema.rb` — are regenerated by `db:migrate`.

## Constraints & decisions
- **Namespace every db command per database**, e.g. `bin/rails db:migrate:down:primary VERSION=...`.
  The un-namespaced form fails in a multi-database app.
- **Host vs Docker connectivity:** host-side Rails commands against Docker MySQL must set
  `PRIMARY_DB_HOST=127.0.0.1` — the MySQL client treats `localhost` as a Unix socket
  (`/tmp/mysql.sock`, not exposed by Docker); `127.0.0.1` forces TCP, exposed via `ports:
  ["3306:3306"]`. There is no dotenv gem, so `.env` (`PRIMARY_DB_HOST=db`) is loaded only by Docker
  Compose; host commands otherwise use `database.yml` defaults.
- **Generated schema files** use double-quoted strings and lack `frozen_string_literal`, triggering
  RuboCop — run `bundle exec rubocop -A` on them after migrating, and correct any stale
  `ActiveRecord::Schema` version to the current Rails version (8.1).
